# NearKey 2FA demo server

Run Node 22+ with `npm ci`, then `npm start`. `npm test` discovers server and browser tests. Runtime dependency is `ws`.

Defaults: `HOST=127.0.0.1`, `PORT=5173`, `PUBLIC_ORIGIN=http://localhost:5173`. Fixture credentials: `admin` / `mint-river-otter-47`; override `DEMO_USERNAME` and `DEMO_PASSWORD` for a deployment. A password match creates a ten-minute pending login. An active setup-page connection keeps its pending login alive and uses a browser-session cookie. Only an enrolled phone's valid Bluetooth login proof promotes it to an eight-hour authenticated session and refreshes the browser cookie for that lifetime. Protected account/dashboard data requires that completed second factor.

For Android, use a trusted HTTPS endpoint reachable by both devices. Set `PUBLIC_ORIGIN` to that exact browser-facing origin and configure the app with the same origin. The reverse proxy must forward WebSocket upgrades and Authorization headers. The server does not trust forwarded headers, allow CORS or permit non-local HTTP browser origins. For USB debug development, `adb reverse tcp:5173 tcp:5173` forwards the Android phone's localhost port to the Mac server. The debug app may use `http://localhost:5173` for HTTP/WS; Mac Chromium opens the same origin. This forwards the network channel only; Bluetooth proof still uses the physical radio. See the [Android USB workflow](../android/README.md#usb-debug-workflow).

For Wi-Fi debug development, `npm run start:wifi` binds to `0.0.0.0` and advertises a private IPv4 address in pairing responses. The browser stays on localhost for Bluetooth; the debug Android app uses the advertised HTTP/WS endpoint. `PHONE_ORIGIN` overrides that address and permits exact HTTPS, loopback or private IPv4 HTTP origins. Browser-origin checks remain tied to `PUBLIC_ORIGIN`. Both devices must share a reachable network; release Android builds require HTTPS.

The command-line server persists enrollment in `.data/phone.json` under the repository root; `PAIRING_FILE` overrides the path. It stores only the account/browser-origin binding, phone identity, label, P-256 public key and native connection credential. Writes use a private temporary file (0600), flush its contents, and atomically rename it before acknowledging enrollment or committing replacement. Newly created storage directories use 0700. Keep the file private and backed up, and run only one server per file. It is excluded from Git and is never a static web asset. Missing storage permits initial enrollment; corrupt data, read errors or account/origin mismatch fail startup. A failed save leaves existing enrollment and sessions unchanged.

Restart resets sessions, temporary pairing codes, challenges, app entries and verification activity, while retaining the enrolled phone and its credential. The foreground Android app can reconnect using its existing registration; the next browser login must still complete a fresh Bluetooth proof. Direct `createApp()` callers remain isolated in memory unless they pass `pairingFile`. Upgrading an already running in-memory server requires one final enrollment, since that older process never wrote its pairing to disk. No password-only phone replacement/removal API exists. Offline recovery requires stopping the server, deliberately resetting its pairing file and the Android local registration, then enrolling again; this is a demo recovery operation.

Bounds: 4 KiB JSON bodies, 8 KiB headers, five-second body timeout, 16 live sessions, one pairing code, one 60-second active login challenge, 100 recent challenge records and 1,000 successful verification activity records. Older challenge IDs return not-found after eviction. Each address has 240 HTTP requests/minute, 10 combined login/enrollment attempts/minute and 20 channel upgrades/minute. A reverse proxy shares these budgets because forwarded addresses are not trusted. Address limiter is bounded to 1,024 buckets. WS payloads are at most 2 KiB; the native phone channel accepts only `{type:'ping'}` messages, at most 60 per heartbeat interval. The setup-page channel accepts no messages.

Initial setup requests with `pageScoped: true` have 30 seconds to attach a WebSocket at `/api/pairing-channel/:pairingId`, authenticated with the owning browser cookie and exact browser Origin. Once attached, the code stays valid while that connection is open. Closing the connection, logout, successful enrollment or creating a new code revokes it. Heartbeat failure also revokes a disconnected page's code. Legacy pairing requests and replacement-phone codes keep their five-minute deadline.

Login-challenge and authenticated-session deadlines are absolute; readiness and reconnect never extend them. Session revocation, channel heartbeat failure and expiry cancel pending phone work. Keeping a setup page connected does not promote its login or extend a Bluetooth challenge. Signature verification and session promotion complete synchronously after body parsing, preventing concurrent duplicate completion. Version 2 signatures bind server-owned login context; enrollment remains version 1.

Static resources are regular top-level web assets inventoried at startup, plus the explicitly allowed bundled fonts `/web/fonts/dm-sans.ttf` and `/web/fonts/manrope.ttf`. Symlinks and arbitrary filesystem paths are not served. `/` serves `web/index.html`; `/shared/protocol.mjs` is the only exposed shared resource. Restart after adding static assets.

Automated tests exercise real P-256 keys, DER SPKI/DER ECDSA, HTTP/WebSocket and pending-login security transitions. They do not exercise Bluetooth radio behavior. Mac Chromium ↔ foreground Android GATT/Keystore is a separate manual hardware gate. This prototype does not integrate external relying-party services or provide production account recovery.
